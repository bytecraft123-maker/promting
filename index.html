Introduction to Prompt Engineering ✨

“ A language model produces a continuation of the information it receives. Prompt engineering is the practice of making that continuation useful, relevant, and reliable.

🤔 The Central Question & Core Concept

Give a model the opening words “The most important discovery of the experiment was…” and many continuations are possible: a technical lab report, a science-fiction novel, or a brief executive summary. The surrounding prompt decides which one you get.

Prompt engineering goes far beyond clever phrasing. In real applications it covers context retrieval, conversation state, output constraints, and validation of the results.

Seq2Seq & Attention Bottlenecks

Early RNN/LSTM encoders squeezed long sentences into one fixed-size thought vector. Attention let decoders look back at every input representation with different weights at each step.

How Language Models Work 🧠

#

Tokenization

LLMs don’t read words; they read token IDs for text fragments. This affects context budget, price, character-level tasks, and other languages.

🌡️

Temperature & Softmax

Logits become probabilities. Temperature sharpens or flattens them: 0.0 is greedy, 1.0+ adds variety.

⚠️

Hallucinations

Fluent text isn’t guaranteed true text. Errors range from invented API parameters to believable citations that don’t exist.

🎛️ Play with temperature

Next word for: “The most important discovery of the experiment was…”

🎚️ Temperature Heuristics Guide

SettingUse CaseBehavior & Trade-offs
❄️ 0.0 – 0.3Factual extraction, math, code formattingVery stable, repetitive phrasing, lowest hallucination risk.
🌤️ 0.5 – 0.8General writing, summaries, Q&A chatNatural variation with balanced coherence.
🔥 0.9 – 1.3Brainstorming, storytelling, poetryWide creative range, higher risk of incoherence.

Chat Models, Human Feedback & Tools 💬

💡 Big idea: A base model completes text. A chat assistant is a model trained and packaged to join a structured conversation, follow instructions, and cooperate with tools.

🔄 From “continue this text” to “help me with this task”

Given What is a good indoor activity for a family of four? a base model might continue it as a questionnaire, a blog post, or a list of more questions. The user wants an answer. Pick a model type to see the difference:

What is a good indoor activity for a family of four?
What is a good outdoor activity for a family of four?
What are the best games for a rainy day?
…

Behavior: continues a text sequence.
Challenge: may continue the document instead of answering the question.

A board game night, baking together, or a family movie.

Behavior: responds to requests in useful formats.
Challenge: weaker explicit structure for multi-turn dialogue.

Here are three ideas: 1) board-game tournament, 2) bake a pizza together, 3) build a blanket fort.
How old are the kids? I can tailor the suggestions.

Behavior: processes role-labeled messages with conversational context.
Challenge: still needs grounding, careful instructions, and safe tool handling.

Chat is not a different mathematical species. The generator still predicts tokens; training and message formatting change which continuation it learns to produce.

🎯 1. What is alignment trying to do?

A web corpus contains excellent explanations, wrong claims, arguments, jokes, and dangerous advice. A base model’s training goal is not a helpful assistant’s goal. Tap each letter of HHH:

Respond to legitimate user goals.

Avoid unsupported claims and acknowledge uncertainty.

Avoid contributing to unnecessary harm.

Aligned does not mean pleasant prose. The aim is behavior that suits conversation and decision support.

🏭 2. The pipeline: SFT → feedback → RLHF

Step through the classical reinforcement-learning-from-human-feedback pipeline:

Supervised fine-tuning. Humans write or pick examples of a good response.

User: Explain a black hole to a twelve-year-old.
Assistant: Imagine a place where gravity is so strong that even light cannot escape…

The model stops learning any plausible continuation and learns the pattern of a good assistant response.
✅ Clearer instruction following. ⚠️ Examples alone do not ensure correctness or judgment everywhere.

An SFT model generates several answers to one prompt and people compare them. Comparing is more informative (and easier) than writing a perfect answer every time. Try it in the game below ⬇️

A reward model learns to estimate which outputs humans prefer and assigns scores to guide optimization.

⚠️ The reward is not an objective test of truth. Preferences can be incomplete, inconsistent, or swayed by presentation style.

The instruction-following model is optimized with the learned preference signal. The slides highlight PPO (Proximal Policy Optimization) as the classical method.

⚖️ 3. Benefits and trade-offs of RLHF

Gains: better instruction following, appropriate refusals, more calibrated uncertainty. Open each trade-off:

🎭 Preference bias

A small group of annotators can shape the model’s style.

🧮 Reward-model limitations

A numerical score may miss subtle factual errors.

💸 Alignment tax

Optimizing for assistant-like behavior may weaken some capabilities or flexibility.

🚫 No absolute guarantee

Training reduces some problematic behaviors but does not eliminate errors.

That is why evaluation stays essential across the application lifecycle.

🎭 4. Chat messages have roles

A conversation is not one long unlabeled text. Roles reduce ambiguity: the model can tell a user request from an earlier reply or a tool result.

System

High-level instructions and application behavior.

User

The person’s request or follow-up.

Assistant

Replies, incl. intermediate tool requests.

Tool

Results returned by an external service or function.

🛠️ 7. Tools extend the conversation

Two interleaved conversations: the visible one (user ↔ assistant) and the application–model one (instructions, retrieved context, tool descriptions, tool results). The model requests an action; the software executes it and returns the result. Step through “When is the next train?”:

“When is the next train?” The model alone has no live timetable.

Search, retrieve, check. Lower risk.

✅ Check your understanding
1. Why might a base model continue a questionnaire instead of answering?
It predicts the most plausible continuation of the text it sees. A question can look like the start of a list of questions.
2. Reward model vs. supervised example?
A supervised example shows one good answer to imitate; a reward model learns to score outputs from human comparisons.
3. What does a message role add?
It tells the model who is speaking and whether text is an instruction, request, reply, or tool result.
4. Who runs an API call?
The application. The model only proposes the call and interprets the result.
5. Why is confident not the same as verified?
Fluency and confidence come from style; verification needs evidence, tools, or checks.

Designing Applications with Language Models 🧩


💡 Big idea: The model produces text; the application turns a real-world problem into the right model input and the output into a useful result.


🔁 1. Think in loops, not isolated prompts
A prompt is one interaction. An application is a process bridging the user domain (documents, preferences, code, decisions) and the model domain (tokenized input, instructions, context, output). Click through the loop:
The user states a goal. It is rarely a ready-made prompt.
The application understands the request and prepares context.
Relevant context and instructions are assembled into one prompt.
The language model generates output.
The app validates, transforms, or acts on the output, then shows the result. The loop continues with the next interaction.
A proofreading assistant may need one pass; a travel assistant needs many steps, external services, and remembered preferences.

Principle: as abstraction, external context, and state grow, the application must do more than forward a message.
📐 3. Four requirements of an effective prompt
1️⃣ A familiar format
Shape the prompt like a recognizable task, document, or dialogue: the Little Red Riding Hood principle. Familiar patterns make the expected continuation easier to infer.
2️⃣ Enough relevant information
Supply what is needed to solve the problem without a flood of unrelated details.
3️⃣ A clear direction
Say what to accomplish and how the answer should begin or be organized.
4️⃣ A controlled stopping point
Define the scope so the model knows when it is finished.
Check them separately: perfect formatting can still lack the data needed for an accurate answer. Build “My computer is slow. Help.” into an operational prompt:

🧪 4. Feedforward: preparing the model’s input
Here “feedforward” is the application’s preparation pipeline, not the transformer’s internal feed-forward block.
Context retrieval: collect useful information.
Example: read the relevant support article.
Snippetization: split long material into manageable excerpts.
Example: extract the paragraph about fan noise.
Prioritization: rank pieces by usefulness and relevance.
Example: device-specific instructions before generic tips.
Prompt assembly: combine task, constraints, and context into the final request.
Where does context come from?
Supplied by the user, e.g. a document to summarize.
From other resources: a knowledge base, an API, or conversation history.
Stable text that ties input together: role instructions, required output structure, reusable constraints. It is the frame, not a substitute for evidence.
🎒 5. Simulator: managing a finite context budget
More context is not always better. Drag the budget and see which excerpts survive when ranked by usefulness. Ranking weighs relevance, priority, freshness, duplication, and cost.
For long chats, keep recent messages and compress older ones into a structured summary. A compact record of the goal, confirmed facts, decisions made, and open questions often matters more than the whole transcript.
🧠 6. Choosing a model is an engineering decision
Use a faster model or precompute stable context.
Use a more capable model and stronger source grounding.
Keep prompts focused; avoid unnecessary repeated calls.
Evaluate task-specific tuning or task decomposition.
A larger model may help, but poorly selected context can still undermine the result.
🔧 7. Turning output into something useful
Output may be a paragraph, JSON, code, or a proposed tool call. Separate generating a proposal from performing an action.
Render a summary with source links.
Display safe, ordered troubleshooting steps.
Turn a structured request into a validated event proposal.
Check generated code with tests before suggesting it.
🚀 8. Advanced loops
Question 1 → Answer 1
      ↓
Question 2 + relevant history → Answer 2
      ↓
Question 3 + updated state → Answer 3
State can hold summaries, prior tool results, user decisions, and task status. One-shot apps discard it.
Question → Retrieve documents → Select excerpts → Ask model → Grounded answer
Retrieval can use keyword indexes or semantic vector search; the query may be reformulated. RAG does not guarantee accuracy: wrong document or misread right one still gives a poor answer.
Require explicit intermediate outputs: 1) identify constraints, 2) gather evidence, 3) compare alternatives, 4) check against constraints, 5) concise recommendation.
Steps should be verifiable. A long explanation is not proof of correctness.
🌐 9. Tools give access to the outside world
A model alone cannot read a live timetable or write to an external server. Tools have defined names, parameters, permissions, and return values.

App → Model: prompt plus available tool definitions.
Model → App: a proposed tool request.
App → Service: a validated API call.
Service → App: the result.
App → Model: tool result plus context. Model → App → User: a useful answer.

ReAct joins reasoning about the task with external action, iteratively. Useful when no single static prompt can hold the answer.
📈 10. Evaluate the entire application
Good-sounding answers are not enough. Measure utility, reliability, and user outcomes.
  • Accuracy against verified answers
  • Success of generated code on tests
  • Adherence to format and constraints
  • Quality of retrieved evidence
  • Time and cost per task
Some tasks grade automatically; others need humans or carefully designed model-assisted grading. Test the whole pipeline: retrieval or assembly failures can dominate.
Measure how people actually use the app, with telemetry and meaningful indirect signals.

Measure success in the user’s domain, not how elegant the text looks.

🏁 Five takeaways
  1. An LLM application is a transformation loop, not just a prompt.
  2. Context retrieval, selection, and assembly are core responsibilities.
  3. State, RAG, and tools enable more demanding workflows.
  4. External actions require additional validation and controls.
  5. Evaluate successful task completion, not persuasive prose.

🔎 Lexical vs Neural Retrieval
Lexical (BM25 / Jaccard): matches exact keywords and error codes, fast.

Neural Embeddings (cosine similarity): place chunks in a vector space so paraphrases with the same meaning still match.

   
✂️ Chunking & Snippetizing
Split long documents into sliding windows with overlap (e.g. 200 words with an 80-word stride) so context survives across section boundaries.
